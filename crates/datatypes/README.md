# xmlcraft-datatypes

XML Schema Part 2, the datatypes (layer L1, no UI, no I/O, compiles for the web).

- **Built-in types:** `SimpleType::builtin(local)` gives the 45 types of the schema language (`anySimpleType`, the 19 primitive types, the 25 derived ones); the derived ones are defined exactly as the specification defines them, by facets (`integer` is `decimal` with `fractionDigits` 0 and the pattern `[\-+]?[0-9]+`, `NCName` is a `Name` that matches `[\i-[:]][\c-[:]]*`, …), so there is one mechanism for built-in and user types.
- **Checking a value:** `SimpleType::validate(lexical, namespaces)` normalises white space, matches the patterns against the lexical form, maps the lexical form to a `Value`, and checks the facets of every derivation step against the value. A list type checks its items (`item 3: …`), a union tries its members in order. The answer is the value, or a `Violation` that names the validity constraint it breaks (`cvc-datatype-valid.1.2.1`, `cvc-pattern-valid`, `cvc-maxInclusive-valid`, …). A pattern that defines a built-in type's lexical space (`integer`, `NCName`) is reported as a lexical error of that type, not as a pattern facet.
- **Values** (`Value`): strings, booleans, decimals of any size (`Decimal`), float and double (`NaN` equals `NaN`, `0` equals `-0`), durations, the eight date and time types, `hexBinary`, `base64Binary` (the unused bits must be zero), `anyURI`, `QName` and `NOTATION` (namespace and local part; the prefix is not part of the value), and lists. `Value::equals` and `Value::compare` follow the specification: values of different primitive types are never equal; the order of the date and time types is partial (a value with a time zone and one without are ordered only if every time zone the second could have gives the same order), and so is the order of durations (a month is not a fixed number of days: `P1M` and `P30D` are in no order, `P1Y` is longer than `P364D`).
- **Dates and times:** the seven-property model with defaults that make the order of the values the order of the periods (a `gYear` starts on 1 January, a `time` is a time on 31 December 1972, …); `24:00:00` is the start of the next day; there is no year 0; years of up to 18 digits are read, and leap years are the Gregorian ones for any of them (chrono does the calendar; a year outside chrono's range is moved by whole 400-year cycles and back).
- **Making types** (`restrict`, `list_of`, `union_of`): a restriction takes the facets as a schema writes them (`FacetSpec`, each with its `fixed` flag), reads their values with the base type, and refuses what the schema component constraints refuse: a facet that does not apply to the base (length on a number, digits on a string, bounds on a string), a value that is not valid for the base, `minLength` over `maxLength`, a facet that loosens the base type's (`maxLength` over it, `whiteSpace` less strict), a `fixed` facet that changes, both `maxInclusive` and `maxExclusive`, bounds that leave no value or that cannot be compared. All the mistakes are returned, not the first. A list of lists is refused.
- **Not here yet:** `ID`/`IDREF`/`ENTITY` as document-level constraints (uniqueness, reference resolution) are the validator's job (the type says it derives from `ID` via `is_derived_from_builtin`); `NOTATION` must be restricted by an enumeration and the notation must be declared (the schema reader); the fundamental facets (`ordered`, `bounded`, `cardinality`, `numeric`); XSD 1.1 types (`dateTimeStamp`, `yearMonthDuration`, `dayTimeDuration`, `precisionDecimal`); an `anyURI` check stricter than "nothing a URI can never hold"; years beyond 18 digits.

Tests: `tests/lexical.rs` (every built-in type's lexical space and what it is the value of), `tests/temporal.rs` (dates, times and durations: validity, equality, the partial orders, canonical forms), `tests/derive.rs` (facets, restrictions, lists, unions, and the constraints on them), `tests/names.rs`, `tests/properties.rs` (nothing panics; canonical forms read back; the orders agree with chrono and with integer arithmetic).
