# XmlCraft roadmap

**Stage: pre-alpha** · now: M1 (text editor and XML syntax); M0's release dry run builds all six targets, install-and-launch is verified on Windows ARM64 only

> **Last reviewed:** 2026-10-27 · **Last updated:** 2026-10-27 · **Change:** M1.10b (comment toggle, expand selection) · **Target:** Altova XMLSpy (feature set described in its public documentation)

XmlCraft is a clean-room, open-source XML editor in the spirit of Altova XMLSpy, built in Rust with egui, like its sibling [PdfCraft](https://github.com/storytold/pdfcraft). The first release (0.1.0) is an XML editor with XSD and DTD support, validation, schema generation from XML, and sample XML generation from schemas. JSON and YAML follow.

## Headline numbers

- **Feature breadth: 6.6% shipped** (10 shipped and 27 partial of 152 counted features; 64 P0, 48 P1, 25 P2, 15 P3; 10 out of scope), 15.5% with partial counted half, from `cargo xtask parity`. The editor now opens, edits, colours and saves XML files byte-faithfully; validation, schemas and generators are not there yet.
- **W3C xmlconf** (XML 1.0 fifth edition, non-validating, namespace-aware): not-well-formed **64.7%** (658 of 1017), valid **100%** (721 of 721), invalid **100%** (227 of 227); the 359 known failures all need the DTD (M2). xsdtests start with M3.

## Progress log

- 2026-10-27: M1.15 large files, first part. Above 1 MiB the highlighter no longer reads every line before a far one: it looks 256 KiB back for a `<!--` or `<![CDATA[` with no closer after it and starts there (`FarJump`, `Highlighter::set_far_jump`; the estimate is replaced by the real state when reading reaches it; a property test shows it agrees with reading everything when no comment or CDATA section goes over lines). The first look at the end of a 100 MB document is 0.23 ms (was 1.2 s; target 16 ms), `Buffer::longest_line_bytes` replaces a per-line loop for the first frame (30 ms), and `fold_ranges` works from a table of line starts instead of the rope, which brings analysing 1 MB back to 25.7 ms (30 ms) with the fold ranges in. Gap 18 narrows to the estimate's rare wrong colour; what is left of large-file mode is the streaming outline and validation above 32 MB (gap 17) and a notice in the window.
- 2026-10-27: `cargo xtask bench`: the editor's performance targets (plan §3) measured on deterministic synthetic documents, in release mode, against `xtask/baselines/bench.toml` (a budget per scenario and a target where the plan names one; a budget above its target is a known shortfall and is only ever lowered). First numbers on this machine: opening a 100 MB file 0.13 s (target 3 s), a keystroke in a 1 MB document and the visible lines coloured 0.04 ms at the 95th percentile (8 ms), analysing 1 MB 26 ms (30 ms; fold ranges included) and 10 MB 0.3 s, pretty-printing 1 MB 25 ms. The one that misses its target is the first look at the end of a 100 MB document, 1.2 s against 16 ms: new gap 18, closed by large-file mode (M1.15).
- 2026-10-27: M1.10b comment toggle and selection by structure. `Editor::toggle_comment` (⌘/) wraps the lines the carets touch in `<!-- -->` from the first character that is not blank to the end of the last line, or takes the markers off when they are exactly one comment (one block per group of touched lines, the carets kept in their text, one undo step); a text with `--` in it is refused and nothing changes. `Editor::expand_selection` (⌥⌘→) grows each selection to the smallest thing of the syntax tree that holds it and is bigger (word, token, value without and with quotes, attribute, tag, element content, element, outwards; it parses the text when asked, not above 8 MiB) and `shrink_selection` (⌥⌘←) goes back the way it grew, until the text or the selection changes. Headless: `doc_select`, `doc_expand_selection`, `doc_shrink_selection`, `doc_toggle_comment`. Shortcut labels write `/` and the arrows as characters.
- 2026-10-27: M1.10a closing tags and smart indent. `Editor::type_input` now also writes the end tag when `>` ends a start tag (caret between: `<a>|</a>`; not for `/>`, an end tag, a declaration, a value or a comment, nor where the end tag is there already) and completes `</` to the end tag of the element that is open (read by parsing the text before the caret). `insert_newline` indents one level after a start tag, in the document's own indentation and line ending, and between a start tag and an end tag gives the content a line and the end tag one of its own. Settings `auto_close` and `smart_indent` turn them off. The editor property test types with all of it, key by key. `doc_type` and `doc_key` do the same headlessly.
- 2026-10-27: M1.9c folding. The editor model has folds (`Fold`: a stretch of the text from the end of the line that stands for it to the end of the last line it hides) and a `FoldMap` that turns lines into rows and back (a property test checks it against a list of the visible lines); folds move with the text through every edit, undo and redo (`History::undo_applied`/`redo_applied` say which edits were made), one that an edit touches opens, a caret that lands in one (a jump) opens it, and movement keeps to the rows (up, down, page, left, right over a fold). `xmlcraft-engine::folding` makes the ranges from the syntax tree (elements whose end tag is on a line of its own keep that line; comments, CDATA, processing instructions and DOCTYPEs; one range per starting line, capped at 50,000) and the commands on them (fold, unfold, fold all, unfold all, fold to a level); the analysis carries them. The widget draws rows rather than lines, a "…" mark on the line that stands for a fold, and chevrons in a strip at the right of the gutter (a click opens a fold itself and reports a click on something foldable to the host, which folds it from the analysis of the text as it is). The app waits for that analysis when the text has changed since the last one (`after_analysis`: it also does the jump to the matching tag), and drops the command if the text changes again. Registry: Fold and Unfold (⌥⌘[ and ⌥⌘], the first shortcuts with Alt), Fold All, Unfold All, Fold Level 1 to 3; tools `xml_folds` and `doc_fold`. `Buffer::line_of` no longer panics for an offset inside a character (found by the outline property test through the new code).
- 2026-10-27: M1.9b auto-pairing of attribute quotes. `Highlighter::mode_at(buffer, offset)` (L1) says where in the markup an offset is (content, tag, attribute value and its quote, comment…) by lexing from the start of the line with the cached modes of the lines before it; a property test checks it against lexing everything before the offset from the top. The `Editor` (L5, now depending on the syntax crate) keeps one and forgets the lines from every change. `Editor::type_input` is what the keyboard does (the widget's text events use it; an input method's commit and a paste do not): in a tag, a quote after `=` writes both quotes with the caret between, the closing quote steps over the one that is there, and Backspace between an empty pair removes both; each caret decides for itself, and `Settings::auto_pair` turns it off. Headless: `doc_type` types as the keyboard does (a line feed is Enter, a tab is Tab) and `doc_key` presses Backspace, Delete, Enter, Tab or Shift+Tab. The editor property test now types with the aids too.
- 2026-10-27: M1.9a matching tags. The analysis now records where each element's start tag and end tag are (`OutlineItem::start_tag`, `end_tag`, `end_name_range`) and answers `Analysis::matching_tag(offset)`: the tag the offset is in (or just after, or just before) and the other tag of its element, by bisection over the start tags and a walk back for the end tag; a mismatched end tag still goes with its element, as the parser pairs them. The editor highlights both tag names when the single caret is in or next to a tag (and the analysis is about the text as it is), ⇧⌘\ goes to the other tag at the same place in its name (waiting for the analysis if the text just changed), and `xml_matching_tag` answers the same headlessly for a position in text, a file or a document. Property test: the pairs are symmetrical for any tag soup and any offset. `shot --goto LINE:COL` puts the caret for a screenshot.
- 2026-10-27: Windows CI fix. Two tests that only ran green on macOS and Linux failed on the Windows runner of main: one expected `/no/such/file.xml` in an error message (the confinement rebuilds a path from its components, so Windows writes `\no\such\file.xml`), the other read a directory to provoke "unreadable" (Windows answers differently by directory). They now check the file name, and read a file that is not text.
- 2026-10-27: M1.11 fix: the formatter no longer formats an `xml:space="default"` island that sits inside a mixed-content element within a preserved region (the walk for islands went through the mixed element, whose subtree is otherwise left alone). Found by the format property test (a new seed is recorded), shown to fail before the fix, and 30,000 property cases pass after it.
- 2026-10-27: M1.8 find and replace, next occurrence. `xmlcraft-editor::find` compiles a `Query` (text or regular expression, case, whole word) into a `Matcher` with bounded size and match counts; a text search is the escaped regular expression, so case folding and word boundaries are the engine's Unicode-aware ones. On the `Editor`: select next and previous match (wrapping), replace the selected match and move on, replace all in one undo step (`$1` groups in a regular-expression search), a caret on every match, and ⌘D (the word, then the next occurrence). The app has a find bar above the editor (⌘F; ⇧⌘H adds the replace row; Enter and F3 step; options Aa, W, .*; a counter such as `2 of 5`; an invalid pattern says why) and every match is highlighted in the text (up to 10,000 matches in a document of up to 4 MB, also a match across lines; above that the matches on each line drawn); the headless tools `doc_find` and `doc_replace` do the same. Property test: a literal search agrees with `str::match_indices` and replace-all with `str::replace`. Not yet: searching only the selection from the bar, find history, find in files (M6), column selection.
- 2026-10-27: M1.11 + M1.14 the formatter, the tools and the CLI. `xmlcraft-format` (L4) pretty-prints and minifies as minimal edits of the white space between nodes and nothing else: one node per line and one level deeper in an element that has no text of its own, one top-level node per line, blank lines kept as one; mixed content (text, references or CDATA beside child elements), `xml:space="preserve"` and the DOCTYPE are left alone and broken markup is refused. Property tests on random documents: only white space changes, the result is well-formed, formatting is idempotent, untouchable subtrees come out byte for byte. XML ▸ Pretty-print and Strip White Space are one undo step in the document's own indentation and line ending. The automation table grew by `doc_open`, `doc_new`, `doc_list`, `doc_text`, `doc_edit`, `doc_set_text`, `doc_undo`, `doc_set_encoding`, `doc_save`, `doc_close`, `xml_wellformed`, `xml_outline` and `xml_format`; saving never replaces a file that changed on disk, one whose bytes were not valid, or a character the encoding cannot hold without being told how; every path goes through `--root`. `xmlcraft-cli check FILE…` prints `file:line:column: severity: message` (exit 1 on errors) and `format FILE [--minify] [--check | --in-place]` works through the same tools.
- 2026-10-27: M1.13 problems, outline, F7 and Go to Line. `xmlcraft-engine::analyze` parses a text once for its well-formedness and Namespaces diagnostics (sorted) and an element outline (capped at 50,000 items; nesting past 1024 levels stops, as in the tree); the `Analyzer` runs it on a worker thread that keeps only the newest request per document, turns a panic into a failed result, and says which version of the text a result is about. The app asks for an analysis after every edit and shows the result without waiting: wavy red and amber underlines in the editor (`Mark`s of the `LineStyler`), a status-bar badge, a Messages pane (counts, `Ln, Col`, a click selects the problem and gives the editor the keyboard) and an Outline pane (filter, a click jumps). F7 checks at once and opens Messages; ⌘G asks for `line` or `line:column`. Known limits: a result can be about a slightly older text than the one shown, and the underlines are clamped to the text rather than shifted through the edits made since (incremental analysis, M1.15, replaces both); the check is the same background analysis, so F7 never waits on a parse. Found by driving it: a click on a message asked for the editor's focus in the very frame egui takes the focus back from the editor, so the request now waits one frame; the two text fields had no accessible name.
- 2026-10-27: M1.12b the editor in the app. Tabs are real documents; File ▸ New, Open (non-blocking native panel, answered on a later frame as PdfCraft learned the hard way on macOS), Save, Save As, Revert, Close; Edit ▸ Undo, Redo, Select All; files named on the command line open; dropped files open. Nothing is lost silently: a document with unsaved changes asks before it closes, and quitting goes through each such document; saving over a file that changed on disk asks; a character the encoding cannot hold offers character references (an edit of the text, only where one is valid) or UTF-8; dismissing the "changed on disk" question never counts as consent; a quit waits for any other question to be answered; a file whose bytes were not valid cannot be saved over. The status bar shows the caret, selection size, encoding, line ending and indentation. Verified with lifecycle tests on real files (bytes on disk compared), and by driving the real app with `--control`. Still to do for M1.12: recent files, autosave recovery, watching the open files (they are looked at when the window gets the focus back), a single running instance and Apple events, and Edit ▸ Paste. Found by looking: the font's `--` and `-->` ligatures made comments read wrongly, so a line is now split into sections between adjacent punctuation (a document must show what is there).
- 2026-10-27: M1.12a documents. `xmlcraft-engine::Document` reads bytes with the right encoding (byte-order mark, XML declaration, UTF-8; UTF-16 and legacy encodings), takes the file's dominant line ending and indentation for new lines, and writes the same bytes back when unedited: for any bytes whatsoever it is flagged lossy or saving gives back exactly the bytes read (property test). A lossy file cannot be saved over its source. A character the encoding cannot hold is reported, and the user's choices are edits of the text, so the text stays the file: character references (only in character data and attribute values; in a comment, CDATA section, processing instruction or name it is refused) as one undoable step, or another encoding, which also brings the XML declaration in line. A document is dirty when its text state differs from the saved one (undoing back to the saved text is clean again) or its encoding does. `Session` holds the documents (opening an open file shows it, also when reached by another path to the same file; closing shows the neighbour). `xmlcraft-platform` (native only) reads only regular files, with a size limit that also holds while reading, and a stamp taken from the open handle that is read again if the file changed meanwhile; it writes atomically through `craft-atomic` (no staging file left; a symbolic link, even a dangling or chained one, keeps its link) and notices a file changed or removed on disk (size, modification time, and on Unix the inode change time and file identity, so a same-size write that restores the time is seen). The shell wiring (tabs, the editor, Open/Save, unsaved-changes prompts, drag and drop) is next.
- 2026-10-27: M1.7 XML colouring. `xmlcraft-syntax::Highlighter` colours a line at a time from the lexer's mode at the line's start (it remembers the start mode of each line it has seen and lexes forward only as far as the line asked for), with 14 classes (punctuation, element and attribute names and values, references, comments, CDATA, processing instructions, the XML declaration, DOCTYPE and declarations, literals, errors). Property: lexing line by line from the saved modes gives exactly the tokens of lexing the whole text. The editor model reports the first changed line per version, the widget tells a `LineStyler` before drawing, and the shell's `XmlStyler` forgets only what an edit made stale. `SyntaxTokens` (light and dark) are checked for 4.5:1 contrast against the editor background. Looked at in both themes with the `editor_shot` example.
- 2026-10-27: M1.6b `xmlcraft-code-editor` (L7): the egui editor widget over `xmlcraft-editor`. Virtualised (only the lines on screen are laid out; a line over 4096 characters is laid out in a window around what is visible, so a megabyte on one line scrolls like a short one), a fixed gutter with line numbers, current-line wash, selections and several carets, tabs expanded to stops, control characters shown as dots, colouring through a host-supplied highlighter, caret blink, scroll-into-view, mouse (click, shift-click, command-click adds a caret, drag with edge scrolling, double click word, triple click line, gutter click line), keyboard with per-platform bindings (a pure table with tests), clipboard events, and input methods (the composition is drawn at the caret and enters the document, and the undo history, only when committed). The host passes colours; the crate knows no theme. egui kittest tests drive typing, keys, mouse, clipboard, IME, read-only mode and the virtualisation; a `shot` example renders it for a visual check (CJK shows as boxes until gap 11 closes).
- 2026-10-27: M1.6a `xmlcraft-editor` (L5, wasm-clean): the headless editor model. An `Editor` owns the buffer, undo history and one or more carets; every command acts on all carets and a text change is one undoable step. Typing (merging into one undo step), paste (line endings converted; one line per caret when the counts match), Enter with indentation, Backspace/Delete by character cluster (emoji, combining marks and CRLF count as one), word and line deletions (overlapping ones join), Tab/Shift-Tab, cut/copy (whole lines with no selection), movement by cluster, word, line, page and document with a goal column, mouse-gesture selections (click, add, drag, word, line), outside edits (formatter, quick fixes) carried through the carets, and undo/redo restoring selections. Verified against a hand-rebuilt string and for valid carets plus undo/redo consistency under random command sequences.
- 2026-10-27: M1.5 `cargo xtask conformance xmlconf`: fetches the W3C suite (pinned by URL and SHA-256), runs every applicable test through the editor's own path (encoding detection, decoding, parser), and keeps `xtask/baselines/xmlconf.txt` as a ratchet (a new failure fails, and so does a fixed test still listed). First run found 589 of 1017 not-well-formed documents rejected; fixing missing whitespace between attributes, pseudo-attributes and after a PI target, public identifier characters, colons in PI targets, unknown declarations, entity-value references and parameter-entity references inside declarations brought it to 658, with valid and invalid still at 100%. Also: a plain `encoding="UTF-16"` now matches either byte order. A weekly `conformance.yml` runs it, and `cargo xtask ci` runs it when the suite is present.
- 2026-10-27: M1.4 `xmlcraft-syntax` parser: a lossless, error-tolerant `rowan` tree (its text is the input, byte for byte) and 55 diagnostic codes with stable keys, severities, English templates and byte spans: mismatched, unclosed and stray tags, attribute problems, references and characters XML forbids, comments, CDATA, processing instructions, the XML declaration, DOCTYPE structure, and Namespaces in XML 1.0 (unbound or reserved prefixes, empty bindings, duplicate expanded names). No recursion (an explicit stack; past 1024 levels elements stop nesting in the tree but are still matched) and capped diagnostics. Verified against `xmllint` as a black box: 46 known documents and 300 random markup strings agree on well-formedness; namespace-constraint violations are reported as errors here and as non-fatal there, by design.
- 2026-10-27: M1.3 `xmlcraft-syntax` lexer (L1): total, lossless and restartable. Its whole state is a `Mode`; no token spans a line break, so every line start is a checkpoint. Covers tags, attribute values, references, comments, CDATA, processing instructions, the XML declaration, and DOCTYPE with its internal subset. A tag, an attribute value, the XML declaration, the DOCTYPE and a subset declaration that are left open end at the next `<`; an open comment, CDATA section or processing instruction runs to its terminator or the end of the text. Properties: tokens tile any text exactly, lexing restarts at every token boundary, and it always finishes. The M0.11 release dry run built all six targets after the Windows MSI fix (#4, merged).
- 2026-10-27: M1.1 + M1.2 `xmlcraft-text` (L0): rope buffer with checked byte offsets and edits that return their inverse, undo history that merges typing and trims its oldest steps against a memory budget (the newest step is always kept), and that refuses to undo onto text that changed behind its back, line-ending counts and conversion, and encodings (byte-order mark, then XML declaration, then UTF-8; UTF-16; legacy encodings; unmappable characters are reported, never replaced). Property tests: buffer against a `String`, undo/redo through every text, and "any bytes are either flagged lossy or written back identically". M0.11 dry run: macOS and Linux built; Windows failed on a WiX component rule, fixed in PR #4.
