The authoritative assessment of how close XmlCraft is to the leading commercial XML editors. [ROADMAP.md](../ROADMAP.md) summarizes it and [gaps.md](gaps.md) lists every shortfall.

**Scope.** Parity means the *desktop editing* feature set. Out of scope and tracked as `na` in `parity/features.toml` (8 entries, excluded from every percentage): the COM/ActiveX API, Visual Studio and Eclipse plug-ins, the vendor's server product, the vendor's AI add-on, database connectors, the vendor's forms-based editing view, code generation and archive views. Since 2026-11-05 XBRL and the WSDL/SOAP client are in scope (M8, M9).

## How this is measured

- **Feature breadth** is arithmetic over `parity/features.toml`: each feature has a tier (P0–P3), a status (`planned`, `partial`, `shipped`, `na`) and, for `shipped`, evidence that names a passing test. `cargo xtask parity` rejects claims whose commands, tools or tests do not exist.
- **Conformance** is the pass rate of the W3C and OASIS suites, pinned by commit and fetched by `cargo xtask conformance`. The ratchet lists every known failure in `xtask/baselines/`; the pass-rate tables here are copied from the command's output whenever the baseline changes (the valid and invalid totals cannot be derived from the baseline, which lists failures only).
- **"Shipped" means exists and tested**, not "as good as the leading commercial XML editor".

## W3C XML Schema Test Suite (xsdtests, 2007 release for XML Schema 1.0)

`cargo xtask conformance xsdtests [--fetch]` builds the schema of each test group through the same loader and assembler the app uses, validates each instance against it, and compares with the verdicts the working group accepted (tests that were queried, or are neither valid nor invalid, are left out, and so is the group `schZ012_a`, which tests that file URLs are compared case-insensitively and whose verdict is the file system's (a file by another case is that file on a Mac or on Windows and none on Linux): 982). A schema test passes when the schema has an error exactly when the suite says it is invalid; an instance test, when the instance has an error exactly when the suite says it is invalid.

The 682 that fail are listed in `xtask/baselines/xsdtests.txt`; a new failure fails the run, and so does one that is fixed and still listed. What they are is in [gaps.md](gaps.md) (gap 21).

## E-invoice rules (EN 16931, XRechnung)

`einvoice_validate` (`xmlcraft_einvoice::validate`) checks an invoice in stages: well-formedness, detection, the XML Schema of its syntax (UBL 2.1, UN/CEFACT CII D16B), the CEN EN 16931 Schematron 1.3.17 for that syntax, and the XRechnung Schematron 2.6.0 (XRechnung 3.0.2) when the document claims XRechnung. The rules are the publishers' Schematron sources, evaluated by `xmlcraft-schematron` on the `xee` XPath 3.1 engine (the XSLT functions of the rule sets are turned into XPath inline functions). `cargo test -p xmlcraft-einvoice --test coverage -- --ignored --nocapture` measures, per rule set, how many assertions exist, how many the engine compiles, and how they come out on the synthetic XRechnung fixtures (`crates/einvoice/tests/fixtures`), measured 2026-11-11:

| Rule set | Assertions | Compile | On the fixture: fired / passed / failed / not fired / not evaluated |
|---|---:|---:|---|
| EN 16931 UBL 1.3.17 | 982 | 982 | 863 / 863 / 0 / 119 / 0 |
| EN 16931 CII 1.3.17 | 810 | 810 | 623 / 623 / 0 / 187 / 0 |
| XRechnung 2.6.0, UBL (14 XSLT functions, all translated) | 77 | 77 | 35 / 35 / 0 / 42 / 0 |
| XRechnung 2.6.0, CII (14 XSLT functions, all translated) | 74 | 74 | 37 / 37 / 0 / 37 / 0 |

Broken variants of the fixtures are reported with exactly the rules they break, at the element they are about (BR-CO-15 wrong total, BR-DE-15 no buyer reference, BR-S-02 and BR-DE-16 no seller VAT identifier, BR-DE-1 no payment instructions, BR-CL-01 a wrong type code; `crates/einvoice/tests/validate.rs`). What this does **not** measure: whether each outcome agrees with the reference implementation (no Saxon/SchXslt run has been compared; there is no oracle in CI), and the rules the fixtures do not reach (the "not fired" column: allowances, charges, other VAT categories, credit notes, the extension and CVD profiles). One defect of the engine is known and affects rule outcomes: it refuses `normalize-space()` and `string-length()` without an argument on a node, which `xmlcraft-schematron` works around by writing them out as `f(string(.))`, their definition. (A second one is fixed: the published `xee` answered `NaN gt x` and `NaN ge x` with true, so a rule comparing `number()` of a missing value could pass; the vendored `xee-interpreter` compares NaN as XPath says, M9.12.) A check the engine cannot compile or evaluate is reported as not evaluated with its reason and is never counted as passed or failed. Not bundled, so not measured: the Peppol BIS Billing 3 rules and the FatturaPA schema (their publishers' terms reserve redistribution, AGENTS.md §1.6).

## W3C XML conformance (xmlconf, 23 September 2013)

`cargo xtask conformance xmlconf [--fetch]` runs the applicable tests of the suite through the same path the editor uses (encoding detection and decoding, then the parser, the DTD reader and the validator, with the external parts of the DTD read from the suite's files) and compares the failures with `xtask/baselines/xmlconf.txt`. Applicable means XML 1.0 fifth edition, namespace-aware: XML 1.1 tests (266), tests for earlier editions only (312), processor-dependent `error` tests (33) and namespace-unaware tests (9) are skipped. A not-well-formed test passes when a well-formedness error is reported; a valid test when no well-formedness or validity error is reported; an invalid test when the document is well-formed and a validity error is reported. External general entities are not read in content (their content is taken as unknown), and the validity errors are not compared with the test's section, only counted.

| Kind | Passed | Of | Rate |
|---|---:|---:|---:|
| not-wf | 1017 | 1017 | 100% |
| valid | 721 | 721 | 100% |
| invalid | 227 | 227 | 100% |

The baseline is empty. How the 359 not-well-formed tests that needed the DTD closed: the DTD reader (M2.6, 306), the rules that tie references to declarations (M2.8, 51: an entity must be declared where the document has all of its declarations and always when standalone, parsed, not external inside an attribute value, without `<` in one, not recursive, with a replacement text that is well-formed where it is used) and the namespace declarations read as the DTD makes them (M2.9, 2: entities in the value of a declaration, and a type that trims it). The invalid tests are caught by: no DOCTYPE (73), an element that is not declared or not complete or not allowed (about 50), attribute declarations and values (about 50: types, defaults, enumerations, ID and IDREF, ENTITY, required, fixed), the standalone document declaration (14), the nesting of parameter entities in declarations, groups and conditional sections (9), and the validity constraints on the declarations (duplicates, ID and NOTATION rules, undeclared notations; about 20).
