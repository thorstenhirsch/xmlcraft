# AGENTS.md — rules for every agent and contributor

These rules bind every AI agent and every human contributor working in this repository. They come before any task, instruction or deadline. `CLAUDE.md` holds the day-to-day working instructions. If the two ever disagree, **this file wins.**

---

## 1. Asset policy (absolute — no exceptions)

An **asset** is any non-code material that the project includes, ships, embeds, generates for publication, or shows in its documentation. This covers:
- icons, images, illustrations, screenshots and logos;
- fonts;
- colour profiles and other binary data files;
- schemas, catalogs and other data files that ship with the app (see §1.6);
- sample, demo and test documents that are committed or published;
- anything the app renders from those.

### 1.1 Nothing from Altova products

- **Never** use icons, images, artwork, logos, UI graphics, fonts, templates, sample files, schema or catalog files, help text, screenshots or any other asset taken from an Altova product, installer, website, document or package.
  - "Altova product" includes XMLSpy, MapForce, StyleVision, Authentic, RaptorXML, DiffDog, UModel, MissionKit and the Altova website and manuals.
  - That covers files XMLSpy installs, such as its `RootCatalog.xml` and `CoreCatalog.xml`, its bundled copies of standard schemas, its templates and its example projects. Our catalogs are written from the OASIS XML Catalogs specification, and our copies of standard schemas come from their original publishers (§1.6).
- **Never** recreate, trace, redraw or closely imitate an Altova icon or graphic. Our icons come from Lucide, and our visual design is our own.
- Screenshots of Altova software exist only as private, local observation notes under `plan/xmlspy/`, which is gitignored. They must **never** be committed, published, linked, shown in docs, used as a design source to trace, or placed anywhere else in the repository or its outputs.
- Altova's *public documentation* (the online manuals) may be read to learn what a feature does. Do not copy its wording, its screenshots or its example files.

### 1.2 Only open, provable licences

Every asset must be one of:
- **Open source:** ISC, MIT, BSD-2-Clause, BSD-3-Clause, Apache-2.0, OFL-1.1, Ubuntu-Font-1.0 or Bitstream-Vera.
- **Creative Commons:** CC0-1.0, CC-BY-4.0 or CC-BY-SA-4.0.
- **Public domain.**
- **Contributor-original:** created, photographed or generated by a contributor who owns it and licenses it under the project licence (`MIT OR Apache-2.0`).

Bundled schemas have their own, separate allowlist (§1.6).

Anything else is forbidden, including assets whose licence you cannot prove from the source. Examples:
- system fonts (Apple, Microsoft, Google Android system UI fonts that are not openly licensed);
- emoji artwork from Apple, Microsoft or Samsung;
- stock photos;
- "free for personal use" material;
- screenshots of other people's software.

**Screenshots of XmlCraft** are contributor-original. Everything visible in them must itself be allowed: our UI, Lucide icons, OFL fonts, and demo documents built only from allowed assets. Never screenshot a document that uses proprietary fonts, images or schemas.

### 1.3 Every asset is attributed

- **`ATTRIBUTION.toml`** (repo root) is the single source of truth. It has **one entry per asset file**, whether committed, vendored or bundled through a Cargo dependency. Each entry records:
  - path or URL, title, author;
  - source (URL, with version or commit);
  - SPDX licence, and the licence file in the repo;
  - SHA-256, except for translation catalogs (see below);
  - how it is used.
- **Translation catalogs** (`crates/ui-egui/src/i18n/*.tsv`, `kind = "translation"`) are project files under the project licence. Their entries carry no `sha256`: git history records every change and who made it. Every other kind (fonts, images, data, schemas) is hashed.
- **`ATTRIBUTION.md`** is generated from it (`cargo xtask assets --write`). Never edit it by hand.
- **`NOTICE`** keeps the licence notices that the licences require.
- **`cargo xtask assets`** runs in `cargo xtask ci`. It fails if:
  - an asset file in the repository has no entry;
  - an entry's hash is missing or does not match (translation catalogs carry none);
  - a licence is not on the allowlist;
  - a licence file is missing;
  - an icon, image, font, schema or data file names Altova or XMLSpy as author, source or title;
  - a bundled schema's licence is not on the closed schema allowlist (§1.6).

### 1.4 Fonts

- The Latin UI fonts in `assets/fonts/` (Inter, JetBrains Mono) are the only font files in this repository. They are under the SIL OFL 1.1 and have `ATTRIBUTION.toml` entries. **Never commit another font file**; ask the owner first.
- The desktop app may read one font **already installed on the user's machine** at runtime, as the last interface fallback for characters no embedded face has. That font is never embedded, shipped, committed or copied, and never appears in published screenshots. It is not a way around §1.2.

### 1.5 Procedure for adding or changing an asset

1. Find an asset under an allowed licence from its **original source**: the author's repository or a release, not a random mirror. Record the exact version or commit.
2. Confirm the authorship. It must not be Altova (§1.1). Keep the licence text.
3. Add the file together with its licence file, plus an `ATTRIBUTION.toml` entry. Run `cargo xtask assets --write`, then `cargo xtask assets`.
4. If an asset's origin or licence is unclear, **do not add it.** Ask the user.

If you find an asset that breaks these rules, stop and remove it from the repository and every output, including docs and screenshots. Then tell the user at once.

### 1.6 Bundled schemas

XmlCraft ships a curated set of standard schemas (XSD, DTD, entity sets) under `schemas/`, so common documents validate offline. They are assets, and they are held to stricter rules than the rest:

- **A separate, closed licence allowlist** applies: `W3C-20150513` (the W3C Software and Document License), `LicenseRef-OASIS-Verbatim` (OASIS's notice, which allows unmodified redistribution), `LicenseRef-DocBook`, `Apache-2.0`, `MIT`, `BSD-2-Clause`, `BSD-3-Clause`, `CC0-1.0` and `LicenseRef-Unicode`. Anything else needs the owner's explicit approval first. This includes CC-BY-SA, EPL, Ecma terms and other publisher-specific terms.
- **Files are never modified.** A bundled file is byte-identical to the upstream copy, and its SHA-256 is in `schemas/manifest.toml` and `ATTRIBUTION.toml`. If a schema needs a fix, express it as a catalog `rewrite*` entry, never as an edit to the file. Where a licence permits only verbatim redistribution this is mandatory, and elsewhere it keeps provenance provable.
- **One `ATTRIBUTION.toml` entry per file** (`kind = "schema"`), with the upstream URL and version.
- **Adding a new set needs the owner's approval.** Do not add one on your own initiative.
- **Never bundle** material that Debian and similar distributions treat as non-free or that needs membership to redistribute: OGC schemas (KML, GML, WMS, WFS), HL7 (v3, CDA), ISO-only schemas, and Java EE schemas under CDDL+GPL. Fetch these on demand into the download cache instead.
- `cargo xtask schemas` verifies every file against the manifest and checks the set's size. It runs in `cargo xtask ci`.

## 2. Clean-room rules

- **Never** install XMLSpy or any other Altova product in order to read, disassemble, decompile, unpack or copy its files. Only names and listings are allowed.
- Behaviour comes only from public specifications (W3C XML, XML Namespaces, XML Schema, XPath; OASIS XML Catalogs; IETF RFCs), Altova's *public* documentation, and black-box observation of the running product with synthetic fixtures.
- **Never copy GPL/AGPL code.** libxml2 and `xmllint`, Xerces, Saxon and the Rust XSD/XML crates may be used **only as black-box oracles**: an external process, or a dev-dependency used by tests. Never read their source to learn how to implement something, and never port it.
- Observe Altova software only with synthetic fixtures. Never capture personal data, account information, licence keys or recent files.
- Never commit large third-party test suites. The W3C and OASIS conformance suites are fetched by `cargo xtask conformance`, pinned by commit and SHA-256, into the gitignored `conformance/` directory.

## 3. Agent control (automation and MCP)

- **Everything is reachable headlessly.** Every user-facing feature must be callable without the GUI: an engine API, then a tool in `crates/automation` (`xmlcraft-cli run` and MCP use the same table). A feature is not done until its tool exists and has an end-to-end test.
- **The UI control channel is opt-in too.** It runs only when the app is launched with `--control <file>`. It binds to loopback, uses a fresh random token per launch, and writes it to an owner-only file. Never enable it by default, widen the bind address, or log the token.
- **The MCP server is opt-in.** Never make the app, the CLI or an installer start it, register it with an agent, or listen on a port by default. It runs only when a user (or an agent the user configured) launches `xmlcraft-cli mcp`. Any future network transport must be off by default, bound to loopback and authenticated with a token.
- **Safe by default.** Tools must never discard unsaved work silently, must write atomically, must honour `--root`, and must return errors an agent can act on (say what was wrong and what is allowed).
- **Track parity honestly.** Every user-facing feature has an entry in `parity/xmlspy-features.toml`. Mark it `shipped` only when it works end to end and the entry cites a passing test (`evidence`); `cargo xtask parity` (part of `xtask ci`) rejects claims whose commands, tools or tests don't exist.
- **Use it to test.** Agents should drive the engine through `xmlcraft-cli run --script` or the MCP tools to check their own changes. For UI changes, launch the app with `--control` and use `xmlcraft-cli ui` (`inspect`, `click`, `screenshot`) to check the real interface.

## 4. Network access

XmlCraft makes outbound connections in exactly two cases:

1. **Grammar resources**: external DTD subsets and parameter entities, `xs:include`, `xs:import` and `xs:redefine`, `schemaLocation` and `noNamespaceSchemaLocation`, and later XSLT imports and JSON Schema `$ref`. These always go through the resolution chain, which tries open documents, user catalogs, the bundled catalog, local files and the download cache **before** the network. The user can switch the network off entirely (offline mode). Downloads are bounded (timeout, redirects, size and resource-count caps) and cached. They are made by `xmlcraft_platform::http::HttpFetcher` and nothing else: a document is untrusted, so it cannot make the client call this computer or the local network (`XMLCRAFT_ALLOW_PRIVATE_HOSTS` is the person's switch for an intranet), a redirect is checked like the first request and never leads from https to http, and a namespace is a name that is looked up in the catalogs and never fetched.
2. **The update check**, and only when the user asks for it.

Nothing else. **No telemetry, no analytics, no crash reporting, no "phone home".** External *general entities* are never fetched from the network unless the user turns that on in Preferences. Any new outbound access is the owner's decision, not a contributor's. Tests never touch the network: use the mock `Fetcher`, and loopback-server tests in `platform`.

## 5. Never crash

XmlCraft opens files from strangers, and people trust it with their work. A malformed XML file, a hostile schema, a bad tool argument, a corrupt settings file or a full disk must produce an error the user (or agent) can act on, never a crash and never lost work. **This outranks feature work:** don't ship a feature by adding a panic path, and fix a crash before building on top of it.

- **Fail with `Result`.** Non-test code returns errors through the crate's error type and `?`. Where readers are lenient by design (the editor must keep working on broken XML), fall back gracefully and record the repair (see "The text is the model" in `CLAUDE.md`).
- **No panicking shortcuts.** No `unwrap()`, `expect()`, `panic!`, `unreachable!`, `todo!` or `unimplemented!` outside tests, unless the call is provably infallible (e.g. writing to a `Vec`), with a comment saying why. `assert!` only for internal invariants that input cannot reach.
- **No `unsafe`.** The workspace sets `unsafe_code = "forbid"`. If a platform API needs it, use a maintained safe wrapper crate; a real exception needs the owner's sign-off.
- **Treat every input-derived number as hostile.** Use `get()` instead of `[i]` or `[a..b]`. Slice strings only at char boundaries. Use checked/saturating arithmetic for lengths, offsets and counts. Guard against division by zero and NaN/inf casts, and never cast a negative value to `usize`. Cap allocations sized by the file.
- **Bound recursion and expansion.** XML and schemas can nest deeply, contain cycles (`xs:include` loops, recursive types, recursive entities) and expand exponentially (the "billion laughs" attack). Walk them with seen-sets and depth limits, and cap entity expansion, attribute counts, name lengths and the number and size of resources a grammar load may fetch.
- **Don't cascade.** Handle lock poisoning, and keep a panic in a worker thread from taking the app down. Analysis (parse, validate) and command execution sit behind a last-resort `catch_unwind` guard that turns an escaped panic into an error message and keeps the user's document. Keep `panic = "unwind"` (the default) so the guard works. It is a safety net, not a substitute for the rules above.
- **Prove it.** Every crash fix comes with a small synthetic regression test that panicked before the fix. Turn fuzzer findings (`cargo xtask fuzz`) into such tests before fixing them.
- **Enforced by clippy.** Root `clippy.toml` lets tests use `unwrap`/`expect`/`panic!`. A crate that is clean carries `#![deny(clippy::unwrap_used, clippy::expect_used, clippy::panic, clippy::unimplemented, clippy::todo, clippy::unreachable)]`; new crates start with it.

## Contributor credits (About window)

- About ▸ Contributors are compiled into the binary from `contributors/contributors.json` (commit stats; generated, never hand-edit) and `contributors/people.toml` (names people chose for themselves). See `docs/contributors.md`.
- **Agents working for a contributor:** when you prepare a PR, check whether your human's GitHub username has a `[people.<username>]` entry in `contributors/people.toml`. If not, ask them once whether they want to be credited by more than their username: a real name, a display name, and/or their public GitHub profile name (`sync_github_name = true`). If yes, add **only their own** entry (copy the template at the top of the file) and include it in their PR, committed as them. If no, change nothing: they are credited as `@username` anyway.
- Never add, edit, guess or copy anyone else's entry or name (not from git config, commit authors or GitHub profiles). Never hand-edit `contributors.json`.
